## 1. 项目定位

本项目面向轴承设计需求分析。第一阶段先实现一个能够与用户多轮交互的深沟球轴承（DGB）需求分析 Agent：理解应用场景和工况，逐步补齐固定设计条件与工程配置，查询可靠的材料/润滑数据，记录设计要求，并最终形成能够转换为 RoBAS 8.11 拟静力学输入的结构化设计任务。

长期目标是形成：

用户需求 → 对话需求完善 → 结构化设计任务 → 参数优化 → 专业计算校核 → 用户确认 → 二维工程图/三维模型/报告。

**当前只开发第一段：对话需求完善及 RoBAS 拟静力学输入准备。** 参数优化模块暂时独立开发，不加入本 Agent，不在本阶段实现优化算法、优化 Agent 或优化工作流。

| 项目 | 第一阶段决定 |

| 计算模式 | RoBAS 8.11 拟静力学，DATA 中 Mode=-1 |

| 对话目标 | 收集/确认固定输入，补齐工程配置，形成结构化 Design Brief |
| 推荐策略 | Agent 可以推荐；用户未接受前保持未确认 |
| 确认状态 | 业务层只使用 confirmed / unconfirmed 两种状态；来源信息单独记录 |
| 优化目标 | 可以记录用户表达的偏好，但第一阶段不要求确定最终优化策略 |

### 2.1 五个优化变量的 DATA 对应关系与断链

已核对本机 C# 序列化位置、属性标注及留存 DATA。fo/fi 的语义位置分别为 raceCurFac1（外）/raceCurFac2（内），但原版自动属性没有同步 backing fields，DGB SetAnalysisValue 也未赋曲率。Python 半径/Dw 映射不等价于原版有效赋值链；参见 PR-00 报告 B02。

| 优化变量 | 符号 | DATA 字段 | 当前代码中的映射 | 单位/形式 |
|---|---|---|---|---|
| 钢球直径 | Dw | rec 5A.bReDia | BearingRequest.parameters.ball_d_mm | DATA 长度单位为 m |
| 钢球数量 | Z | rec 3.2.nRe | BearingRequest.parameters.ball_count | 整数 |
| 钢球节圆直径 | Dpw | rec 5A.pitchDia | BearingRequest.parameters.pitch_d_mm | DATA 长度单位为 m |
| 外圈沟曲率系数 | fo | rec 5A.raceCurFac1 | 外圈沟道半径 / 钢球直径 | 无量纲 |
| 内圈沟曲率系数 | fi | rec 5A.raceCurFac2 | 内圈沟道半径 / 钢球直径 | 无量纲 |

注意：DATA 中的 rec 5A 对应 0-based 索引 10；rec 3.2 对应 0-based 索引 5。变量命名、内外圈方向、单位和原版 getter 精度必须在 PR-00 复核。五个变量未被优化器提供之前，输入模板不得伪装成可直接运行的完整 DATA.txt，也不得用猜测值填充。

## 3. 第一阶段的完成定义

第一阶段完成时，系统应能通过多轮自然语言交互得到一个经过确认的 DGB 设计需求，并将其转换为 RoBAS 拟静力学输入模板。

### 3.1 设计任务必须包含

1. 轴承对象：DGB、应用场景、型号（若用户提供）和设计边界。
2. 固定几何边界：内径 d、外径 D、宽度 B，以及 RoBAS 输入所需的其他分析几何。
3. 运行工况：内外圈转速、载荷分量和方向、温度、安装/运行条件等；具体必填项以 PR-00 审计后的 DATA 字段为准。
4. 工程配置：游隙、配合、滚动体/套圈/保持架材料、保持架构型、润滑方式、润滑剂及所需物性、密封/精度要求等。
5. 设计要求：用户明确提出的硬约束、希望改善的性能和其他偏好。
6. 优化变量预留：Dw、Z、Dpw、fi、fo 的变量定义及待填标记；不在本阶段搜索或选值。
7. 数据溯源：用户输入、数据库记录、标准条款、审核规则、公式派生、系统配置或参考 DATA profile 的来源。
8. 确认情况：所有需用户接受的值使用 confirmed / unconfirmed；推荐值在用户接受前不能用于最终可运行输入。

### 3.2 不能混淆的三类产物

- **DesignBrief**：完整表达用户设计意图和工程上下文。它可以包含不直接进入 RoBAS 的信息，例如设备工作制度、维护偏好和成本偏好。
- **RoBASInputTemplate**：将 DesignBrief 和经过确认的数据源转换为 43 条拟静力学输入记录的结构化模板，其中五个优化字段明确待优化。
- **Runnable DATA.txt**：只有当全部必需字段都具有可追溯的有效值、五个优化变量已经由后续优化模块提供、协议检查通过时才允许生成。第一阶段不负责提供五个变量，也不运行优化。

如果五个变量未填，系统只能输出模板和缺项报告，不能把空值、零值或旧 profile 中的值冒充优化结果。

## 4. 参数分类与状态规则

### 4.1 参数角色

| 类别 | 含义 | 示例 |
|---|---|---|
| 用户固定条件 | 用户提供并希望保持不变的边界/工况 | d、D、B、载荷、转速 |
| 工程配置 | 用户选择或 Agent 推荐后由用户接受 | 游隙、材料、润滑剂、配合 |
| 计算派生量 | 由已确认输入和明确公式计算 | 几何派生尺寸、物性换算、工作游隙（若公式和数据具备） |
| 优化变量 | 交给未来优化模块提供 | Dw、Z、Dpw、fi、fo |
| 求解器配置 | 拟静力模式、数值控制、输出配置等 | Mode=-1、经过审核的 solver profile |
| 设计要求/偏好 | 用户对性能、寿命、温度、成本等的要求 | 最低寿命、功耗偏好 |

### 4.2 简化确认状态

业务确认状态只保留两种：

- confirmed：用户明确提供或接受了该值；**不等于**工程来源或规则已经审核。
- unconfirmed：Agent 推荐、从候选项中建议或根据不完整信息推断，或用户只给出估计但尚未明确选定分析值。

缺失值保持 null，并在完整性检查中报告；不增加“推荐中”“待审核”等第三种业务状态。

来源和确认状态是不同维度。系统派生值及数据库物性以独立的 evidence_status/source_ref/规则版本说明其可信度，**不能冒充用户确认**。一个推荐润滑剂可以有数据库来源，但在用户接受之前仍为 unconfirmed。

### 4.3 禁止行为

- 不把未填写字段静默解释为 0。
- 不把旧 DATA profile 的继承值自动视为用户确认。
- 不让 LLM 生成材料物性、润滑物性、标准阈值或求解器字段的虚构数值。
- 不将工作游隙等派生量当作普通用户输入，除非用户明确给出目标值或约束。
- 不把“DATA 可以序列化”解释为“计算已收敛”或“工程设计合格”。

## 5. 对话 Agent V1：自主 ReAct 与五工具（覆盖旧固定流程）

最终行为设计详见 [Conversation Agent V1 架构](agent/CONVERSATION_AGENT_V1_ARCHITECTURE.md)，**字段/类型/单位/条件必需规则的唯一合同**见 [DGBDesignBrief/v1 字段目录](agent/DGB_DESIGN_BRIEF_V1_FIELD_CONTRACT.md)。**本版以自主工具循环替换旧的「理解→更新→检查→选择动作→回复」固定五步骤，不另设独立提问规划器或 Supervisor。**

| Agent 可见工具 | 具体职责 | 权限边界 |
|---|---|---|
| `update_design_brief` | 批量记录/修改参数，接受推荐，接受已展示的整份摘要 | 唯一受信写入；PR-01 先实现原子批量更新/内容 revision，操作级幂等后续按需 |
| `get_design_status` | 返回 known/missing/pending_confirmation/conflicts，保留估计值精度 | 仅客观状态；**不返回问句规划/负责人/优先级分数** |
| `lookup_engineering_knowledge` | 查询有来源的型号、材料、润滑、游隙、配合知识 | 模型通用解释可以直接说；精确工程数值需有来源 |
| `recommend_engineering_config` | 在当前受信工况下筛选审核配置并生成推荐包 | 推荐只生成提案，用户接受前不能置为 confirmed |
| `finalize_design_brief` | `check` 生成版本绑定摘要；`export` 导出草案或完整需求 | 用户整份确认交给工具① accept_brief；不能宣称 RoBAS 324 字段已可计算 |

不再设独立 `confirm_recommendation`（合并进工具①）；用户明确选择 V1 **暂不增加** `check_solver_compatibility`；也没有 `question_planner`。

### 5.1 单轮自主工具循环

```text
用户消息 → 加载 DesignBrief 与会话摘要 → Conversation Agent
     ├─ 直接回复/自然语言提问 → END，等待用户
     └─ 自主选择工具 → 受控工具执行 → 结构化结果返回 Agent
                                               │
                                               └── 再次决定调用工具或回复
```

用户回复会开启下一轮。每轮设可调整的调用次数上限与简单重复调用保护；**同一会话每次只处理一轮，所有状态写入串行**。PR-01 先使用 `brief_revision` 记录真实内容变化，PR-02 接入对话回合标识；仅在后续真实出现同轮多写入自动重试需求时增加 `operation_key`，不预建三层事务框架。同轮不同的合法写入按顺序执行，不能被当作重复。工具①成功后顺带返回新状态，通常无需再调用工具②。模型**自主决定问什么和怎么问**，但不能修改客观必需字段定义、伪造用户确认或编造专业参数。

### 5.2 需求引导的柔性原则

根据用户当前意图、已知值、缺失值、冲突、历史回复、推荐前置条件自主选择 1–2 组相关问题；用户主动问知识可先解释，再回到参数收集。普通工况倾向尺寸→转速→载荷→温度→工程配置，但不硬编码为固定问卷。用户不懂材料时查询或推荐而不是重复提问材料名；「电机转速」不自动等于内圈转速，「总重量」不自动等于单轴承载荷。

### 5.3 工程边界

`DesignBrief` 是唯一可信参数来源；`PendingProposals` 仅是待确认方案；`ConversationHistory` 不作为可信参数副本。用户确认状态只有 confirmed/unconfirmed，来源与近似/范围信息单独记录。用户修改工况后相关派生量和旧推荐适用性失效，不擅自修改原有用户选择。

工具⑤只检查用户层需求并允许导出缺项标记的草案；需要用户已看到指定 revision 摘要后用工具① accept_brief 完成整份接受。**完整 Brief、整份用户接受、RoBAS TEMPLATE_READY 和 RUNNABLE_READY 是不同概念**；后续 PR-06 仍独立建立严格工程协议 gate，暂不设 Solver Compatibility 工具不意味着忽略实际模型限制。

## 6. 目标、硬约束与计算能力边界

第一阶段需要记录用户表达的设计要求，但不实现优化策略。

- 用户明确提出的最低寿命、温度上限、最小油膜等要求，先作为需求条目保存。
- 用户表达的“尽可能低功耗”等愿望作为偏好保存。
- 不强制用户在对话阶段确定唯一优化目标。
- 每个要求必须注明：是否可由当前 RoBAS 拟静力学输出直接评估、是否需要派生计算、是否需要其他计算模式/外部方法、是否尚未确认。
- 不能因为某个指标出现在 OUT.txt 或原版结果表中，就默认它已具有经审核的工程判定阈值。
- 优化算法、目标权重、Pareto 方案排序和计算预算策略留待优化模块完成后再定义。

## 7. 知识来源与推荐原则

知识分为三类，不能混成无来源的通用提示词：

1. **RoBAS 原版数据**：材料与润滑实际由 CSV Server 读取；SQLite 为型号、尺寸和规则表。必须记录文件哈希、自然键/主键、列、单位、转换及适用范围；rec8.6/9.7/10不能冒充材料/润滑CSV直接结果。
2. **标准资料**：例如适用的 GB/ISO 标准。必须记录标准编号、版本、条款、适用条件和可引用的公式/表格；未确认适用性前不能作为硬门槛。
3. **审核后的工程规则**：例如高速工况下的材料、润滑、保持架配置建议。必须记录规则依据、适用范围、审核人/状态和版本。

第一版优先使用结构化查询和显式规则。只有在标准文本等非结构化资料确实需要语义检索时再增加 RAG；不为了使用 RAG 而建立大型知识平台。

## 8. 已知 RoBAS 基线与重要缺口

2026-11-20 已检查本机 RoBAS C#、7个资源SQLite、CSV、原版UI和DGB留存案例；Bearing_CAD main基线为4460a784846d7df978579f49e8685a18da336e81。324字段定位证据见PR-00；求解核语义、目标工况覆盖及构建身份仍BLOCKED。

### 8.1 已有证据

- Bearing_CAD 当前有 DGB/ACB 球轴承 43 条拟静力学 DATA 记录结构和字段解析器。
- 球轴承 DATA 使用 Mode=-1；记录包含求解器设置、几何、保持架、材料、工况、润滑/热参数等。
- 已有 DGB/ACB DATA 字段映射文档和输入构建代码。
- 已有 Windows 隔离执行探针、结果解析和本地分析 API。
- 已有 DGB、ACB 和 CRB N 型真实 Windows golden case 证据；本项目第一版只采用 DGB。
- 结果解析能保留功耗、接触、油膜、温度、运动学等多类打印数据，但求解收敛状态仍为 UNKNOWN，不能把进程退出码 0 当作收敛证明。

### 8.2 当前实现不能直接满足的要求

- 现有球轴承 DATA builder 以显式选择的原版 DATA profile 为基线，不是从零推导全部 43 条记录。
- 现有分析 API 的运行工况覆盖有限，主要暴露载荷 X/Y/Z、内外圈转速和自由游隙；其他力矩、错位、温度、配合、热边界和扫描设置仍可能继承 profile。
- 高级设置仅暴露有限材料物性、保持架 pocket/guide 黏度和求解器 load_steps；润滑油黏温曲线、部分热参数等仍留在 profile。
- DGB/ACB CAD 的显式保持架与原版分析保持架尚未完整对应；现有 API 对部分显式 CAD cage 输入会拒绝。
- DGB 分析几何还需要单独的内圈外径等分析几何输入；不能只凭 d/D/B 自动假定所有分析几何。
- 当前代码保留的原版 profile 字段不能未经审查就当作对任意工况适用的默认值。

因此，第一阶段不能简单调用现有分析 API 就声称已经实现完整需求转换。必须先完成 PR-00 字段级审计，再决定是扩展输入构建器、建设明确的 profile 选择/确认机制，还是二者结合。

## 9. 总体架构：单一 Agent + 五工具 + 普通后台服务

```text
Conversation API / 会话加载
       ↓
Conversation Agent（有界 ReAct 模型-工具循环）
       ├── update_design_brief           ← DesignBriefStore（写入+版本）
       ├── get_design_status             ← RequirementChecker（简洁缺项）
       ├── lookup_engineering_knowledge  ← KnowledgeRepository（可信知识）
       ├── recommend_engineering_config  ← RecommendationService（候选提案）
       └── finalize_design_brief         ← FinalizationService（检查+导出）
       ↓
返回用户消息，等待下一轮
```

工具背后可有普通 Python 函数，不等于独立 Agent。推荐工具直接使用知识仓和筛选规则，不必让模型先强制调用知识查询工具。Python3.11+、Pydantic、SQLite 和最小 LangGraph/等价 agent loop 足够；**单进程、单会话串行，不预先实现跨客户端并发控制、分布式事务或复杂异常恢复**；不写空模块、不建立通用规则引擎。RoBASInputAdapter 留待 PR-06，作为独立的计算输入准备能力而非第六个对话工具；**RoBAS 43/324 字段的映射与有限条件校验属于专业适配层，不要求 Agent V1 建动态工程规则系统**。

## 11. 质量与验收原则

每个阶段至少区分以下证据等级：

1. 代码实现完成。
2. 自动化测试通过。
3. 与原版 C# / SQLite / DATA 字段逐项一致。
4. Windows 本机真实 EXE 验证。
5. 轴承专业人员审核工程规则与适用性。

不得将较低等级的证据表述为较高等级的结论。

第一阶段最终验收至少包括：

- 自然语言多轮对话测试：用户已知、未知、范围、修正、冲突、否定、单位混用。
- 确认语义测试：推荐值未接受时不得进入已确认输入；用户修改后派生字段正确失效/重算。
- 知识查询测试：材料和润滑记录必须来自真实数据源，字段/单位完整。
- 输入协议测试：43 条记录、字段顺序、数值单位、Mode=-1、kUnit/kBrg、行尾和格式与原版协议一致。
- 缺项测试：除五个优化变量外，任何必需字段未确定时不得报告模板完整。
- Golden 对照：使用原版 UI 生成的 DGB DATA 和可追溯工况逐字段比较。
- 负面测试：无效 profile、未知材料、缺少物性、单位错误、几何不一致、非有限值和未经确认推荐值均应明确失败。
